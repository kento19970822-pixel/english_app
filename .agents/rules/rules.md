# プロジェクト共通開発ルール & AIエージェント行動規範

## 0. 基本行動規範（最優先）
1. **作業前の認識合わせ・計画提示**:
   - 実装や修正作業に入る前に、必ず「修正方針・設計」「作業手順」を提示し、ユーザーとの認識合わせを行うこと。
2. **要件定義書の適宜更新**:
   - 仕様追加・変更・ステータス更新時は、要件定義書（`D:\dev\projects\english_app\docs\REQUIREMENTS.md`）の情報粒度が低下しないよう、漏れなく更新を行うこと。
3. **作業ブランチの作成推奨**:
   - 必ず作業用途に応じたブランチを作成してから作業を開始・案内すること。
4. **作業の段階的実行と細分化（ステップバイステップ）**:
   - 一度に広範囲の変更をまとめて行わず、機能やタスクを小さなステップ（1機能、1ファイル群ごと）に分割して進めること。
   - 1つのステップが完了するごとに作業を一旦止め、ユーザーへ「実施内容の報告」「次に試すこと（動作確認手順）」「確認後に実行するGitコミット手順」をセットで提示し、認識合わせを行ってから次のステップへ進むこと。
   - ユーザーの確認・合意が得られる前に、独断で次のタスクの実装を進めないこと。

## 1. コミット前の品質チェック必須手順
コードの変更後、コミット指示を出す前（またはコミット実行前）に必ず以下の項目を実施・確認すること。
- **アプリ起動確認**: 実機またはシミュレータ/ブラウザでアプリが正常に起動・描画されること。
- **静的解析**: ターミナルで `flutter analyze` を実行し、エラーおよび警告（Warnings/Lints）が解消されていること。
- **自動テスト**: `flutter test` を実行し、すべてのユニットテスト・ウィジェットテストがパスすること。
- **コミットメッセージ**: 必ずメッセージ冒頭やタグに `[動作確認済]` を含めること。

## 2. ブランチ運用ルール（機能ブランチの原則）
- `master`（または `main`）ブランチへ直接変更を加えないこと。
- 機能開発、仕様改修、リファクタリング、ドキュメント修正の際は、必ず作業用途に応じたブランチを作成して作業を進めること。
  - 機能開発・改修: `feature/機能名` (例: `feature/fix-f00-ui-sound`)
  - ドキュメント更新: `docs/ドキュメント名` (例: `docs/update-requirements`)
  - バグ修正: `fix/バグ名`
- 作業完了後、動作確認・テストを通過したことを確認した上で `master` ブランチへマージし、作業ブランチを削除する手順を案内すること。

### 実行コマンド例（PowerShell）
```powershell
# 1. 作業用ブランチの作成と切り替え
git checkout -b feature/xxx

# （実装作業・動作確認・flutter analyze・flutter test）

# 2. 変更の追加とコミット
git add .
git commit -m "feat: [VER-yyyymmdd-xx] [動作確認済] 変更内容の要約"

# 3. masterへの安全な統合
git checkout master
git merge feature/xxx

# 4. 作業ブランチの削除
git branch -d feature/xxx
```

## 3. CI/CDワークフロー（GitHub Actions）の管理規約
- `.github/workflows/` 配下のワークフローファイル（`.yml`）は、同一目的のものを重複して作成しないこと。
  - Web版公開: `deploy.yml`（GitHub Pages）
  - iOS版ビルド: `build_ios.yml`（IPAビルド）
- 新規ワークフローを追加・変更する際は、既存のワークフローとの重複やトリガー条件（`on.push`）を必ず確認し、多重実行を防止すること。
